# Панель боевых докладов на тактическом экране

Дата: 2026-10-16. Статус: **согласованный объём для планирования; реализация NOT STARTED**.
Источник: обсуждение интерфейса и запрос пользователя «Сохрани это ТЗ в документацию и создай по нему эпик в Board с пользовательскими историями и тикетами.»
Пользователь разрешил подготовку без requirements-engineer. Сохранение и декомпозиция не являются поручением выполнить тикеты или опубликовать код.

Связи: [эпик EP-0010](../../../Board/EP-0010-combat-reports/EP-0010-combat-reports.md), [карта тикетов](../../../Board/EP-0010-combat-reports/Tickets.md), [текущая модель боя](../../01-Requirements/EngineRequirements.md#phase-four-module-combat), [экран GameSession](../Screens/GameSession.md).

## 1. Назначение

Новая панель превращает важные боевые события в наглядные доклады экипажа: иллюстрация произошедшего, портрет докладчика и короткая реплика. Основной сценарий первой версии — «Тетрар против трёх Мух» (`Scenarios/CombatMukha/scenario.json`, имя в текущем контенте Tetrarch vs 3 Mukha). Панель работает дополнительно к существующему журналу.
Взаимодействие — аккордеон по образцу указанного пользователем Crusader Kings III; копирование конкретной графики игры не требуется.

## 2. Размещение и компоновка

**R01.** Панель «Боевые доклады» находится справа непосредственно под блоком корабля игрока и выбранного объекта; совпадает с ним по ширине. Верхняя граница следует за фактическим низом блока, включая свёрнутое состояние.

**R02.** Панель занимает оставшуюся доступную высоту, не перекрывает нижние элементы управления и существующий журнал. При нехватке места использует ограничение высоты и внутреннюю прокрутку. Размер окна и масштаб UI пересчитывают геометрию.

**R03.** До первого события — компактный заголовок и «Боевых докладов пока нет». События относятся ко всему бою игрока. Выбор другого объекта не фильтрует и не очищает панель.

## 3. Карточки и взаимодействие

**R04.** Новые карточки сверху. При наличии событий ровно одна раскрыта; остальные показывают только строку заголовка. Раскрытая карточка содержит заголовок и физическое время события, крупную иллюстрацию, портрет докладчика, имя при наличии, должность, короткую реплику и ключевые доступные факты.

**R05.** Новое событие автоматически раскрывается и сворачивает предыдущую карточку. Щелчок по старому заголовку раскрывает соответствующую карточку; повторный щелчок по раскрытому не оставляет список без открытой карточки. После ручного просмотра старой карточки следующее новое событие снова становится открытым.

**R06.** Раскрытие не выбирает объект на карте, не перемещает камеру, не отправляет игровые команды, не меняет скорость и не ставит игру на паузу. Колесо над панелью прокручивает панель и не масштабирует карту. Ввод в её прямоугольнике не проходит к карте.

**R07.** Несколько событий за одно обновление добавляются в авторитетном порядке; раскрыто последнее. Все остальные доступны по заголовкам, без искусственной задержки показа. Разные снаряды и разные противники сохраняют отдельные карточки.

## 4. События первой версии

| Код | Заголовок | Докладчик | Условие |
|---|---|---|---|
| E01 | «{Противник} в радиусе торпед» | Оператор сканера | Известный вражеский корабль впервые оказывается в геометрической дальности хотя бы одного установленного исправного торпедного аппарата игрока |
| E02 | «{Противник} запустил торпеду» | Оператор сканера | Подтверждён фактический пуск торпеды известным противником, участвующим в бою с игроком |
| E03 | «Торпеда запущена: {Цель}» | Оператор торпедного аппарата | Аппарат игрока фактически выпустил торпеду |
| E04 | «Противоракета запущена» | Оператор ПРО | ПРО игрока фактически выпустила противоракету |
| E05 | «Вражеская торпеда перехвачена» | Оператор ПРО | Подтверждён успешный перехват противоракетой игрока |
| E06 | «{Противник} поражён» / «{Противник} уничтожен» | Оператор торпедного аппарата | Подтверждено попадание торпеды игрока либо уничтожение противника этим попаданием |
| E07 | «Наш корабль получил повреждения» | Капитан | Подтверждено боевое повреждение брони или структуры модуля корабля игрока |

**R08.** E01 — геометрическая дальность, а не гарантия перехвата. Перезарядка, боезапас и выбранная цель не меняют её. Радиус берётся из действующей конфигурации исправных аппаратов; числовой радиус не зашивается в UI. E01 выдаётся один раз на противника за сессию. Повторный вход не повторяет доклад; три Мухи имеют три независимых отметки.

**R09.** E03/E04 появляются после фактического пуска; нажатие кнопки, очередь команды, отказ и пропуск выстрела не создают карточки. Каждый фактический выстрел очереди — отдельный доклад.

**R10.** Попадание, одновременно уничтожившее корабль, создаёт одну E06 с результатом «уничтожен». Бросок, попадание, повреждение и разрушение модуля одного удара не дублируют её. E07 определяется по фактическому уменьшению брони/структуры; нулевое изменение не считается повреждением. Новый показатель Hull HP не вводится. Полный технический журнал сохраняет прежнюю детализацию.

## 5. Реплики и докладчики

| Событие | Пример |

| E01 | «Капитан, „Муха-1“ вошла в радиус действия наших торпед.» |
| E02 | «Зафиксирован пуск торпеды с „Мухи-2“. Цель — наш корабль.» |
| E03 | «Торпеда выпущена. Цель — „Муха-1“.» |
| E04 | «Противоракета выпущена на перехват входящей торпеды.» |
| E05 | «Перехват подтверждён. Вражеская торпеда уничтожена.» |
| E06 — попадание | «Попадание по „Мухе-1“ подтверждено.» |
| E06 — уничтожение | «„Муха-1“ уничтожена. Поражение цели подтверждено.» |
| E07 | «Зафиксировано попадание. Наш корабль получил повреждения.» |

**R11.** Фразы о цели вражеской торпеды, модуле и причине уничтожения допустимы только при наличии разрешённых игроку данных. Данные, доступные Engine, сами по себе не считаются доступными игроку. Посторонние бои не попадают в панель.

**R12.** Карточка фиксирует докладчика и отображаемые имена на момент события. Смена оператора, удаление снаряда или уничтожение корабля не меняют старую карточку. При отсутствии назначенного персонажа — название службы без выдуманного имени. При отсутствии портрета — знак должности. Портреты существующих персонажей переиспользуются только при наличии реальной привязки.

**R13.** Тексты локализуются через существующие Russian/English каталоги. Заголовки и реплики переносятся. Новое событие не перехватывает клавиатурный фокус. Заголовки доступны с клавиатуры, Enter раскрывает выбранный; нажатия вне фокуса панели сохраняют текущий смысл игрового управления.

| player-torpedo-launch.png | Пуск торпеды с корабля игрока |
| player-countermeasure-launch.png | Пуск противоракеты |
| enemy-torpedo-intercepted.png | Перехват и разрушение вражеской торпеды |

| player-ship-damaged.png | Удар по кораблю игрока и повреждение наружных модулей |

**R15.** Единый стиль DSS; изображения без встроенных надписей, имён и чисел. Портрет отдельный. Основное действие различимо в уменьшении. Цвет различает угрозу, своё действие, успех и повреждение; смысл также выражен текстом и значком. При отсутствии иллюстрации — тематическая пиктограмма.

## 7. Архитектура и данные

**R16.** Engine определяет факты, исходы, участников, порядок и физическое время. Contracts передаёт immutable сериализуемые данные. Client выбирает текст, изображения, раскрытую карточку и прокрутку. Render не обращается к Engine. Предсказанные Client координаты не определяют E01 и боевые исходы; тексты журнала не разбираются.

Для доклада доступны уникальный ID/sequence, тип, физическое время, участники, связанный снаряд, корреляция удара, докладчик/служба, разрешённый результат и зафиксированные отображаемые имена. Существующие DTO расширяются только при недостаточности. Графические типы не пересекают границу Engine–Client. E01 требует нового авторитетного факта: текущий CombatEventType не содержит входа в дальность.

**R17.** Повторные snapshots не создают повторных карточек. При одинаковом времени порядок задаётся авторитетной последовательностью. Новые доклады не теряются при coalescing snapshots и временном отставании рендера. Объединяется только один боевой эпизод; разные снаряды сохраняются. Переполнение очереди доставки не допускает тихой потери событий.

**R18.** Правила видимости и работоспособности сканера соответствуют действующим правилам Engine. Новый UI не расширяет обнаружение неизвестных целей и не вводит новую модель сканирования.

## 8. История и жизненный цикл

**R19.** В панели последние 200 карточек; при превышении удаляются самые старые. Ограничение истории UI отдельно от очереди ещё не обработанных докладов.

**R20.** Новая игра и успешная загрузка создают чистую панель. Исторический журнал сохранения не воспроизводится как новые доклады. После загрузки уже находящиеся в дальности противники становятся исходным состоянием и не создают немедленный E01. Выданные ранее E01 не повторяются после загрузки, в том числе для противника, бывшего вне дальности в момент сохранения. Отметки сохраняются авторитетно. Раскрытая карточка и прокрутка не сохраняются. Ошибка загрузки не очищает панель действующей сессии.

**R21.** Переход на Defeat сохраняет приоритет и не задерживается ради показа карточки. Доклады не продвигают часы или RNG, не меняют исход боя. При terminal-состоянии не создают событий мира после момента гибели.

## 9. Производительность и доступность

**R22.** Цель проекта — 80 FPS (12,5 ms на кадр). Новые события обрабатываются при получении данных; изображения и портреты кешируются; файловый ввод и декодирование запрещены в Draw. Число карточек и ресурсов ограничено. Проверяются все поддерживаемые масштабы UI.

## 10. Проверки и границы приёмки

**R23.** Обязательная матрица: все E01–E07 и оба результата E06; три разных противника; повторный вход; множество событий одного обновления; одинаковое время; два разных снаряда; дубли snapshots; пропуск промежуточных snapshots; пуски/очереди/отказы; успешный и неудачный перехват; попадание с уничтожением; нулевое повреждение; скрытая цель; отсутствующие портрет/иллюстрация; удалённый участник; пауза; смена выбора; Save/Load; ошибочная загрузка; поражение.

Автоматические проверки подтверждают факты, порядок, дедупликацию, корреляцию, маскирование, retention и Save/Load. Для каждого типа нужны воспроизводимые условия — случайный исход одного боя недостаточен. Сценарий CombatMukha остаётся обязательной интеграционной основой, без изменения его баланса.

**R24.** Отдельная визуальная приёмка в запущенном Client проверяет компоновку, читаемость, иллюстрации, портреты, ввод и производительность. Минимальная матрица: 1280×720 и 1920×1080, UI 100/120/150%, Russian/English, открытый/свёрнутый Object Info, пустая/полная история. Headless/build не закрывают native/human/FPS gates.

Первая версия включает панель, семь типов докладов, восемь иллюстраций и интеграцию с авторитетными фактами. Озвучка, ответы игрока, автопауза, фильтры и изменение баланса не входят в объём.

## 11. Технические допущения декомпозиции

Ниже — решения планирования, не дополнительные ответы пользователя. Они уточняют выполнение требований, сохраняя продуктовый объём §§1–10.

- **A01 — передача.** Ввести отдельные BattleReportSnapshot/CombatReportBatchSnapshot в Contracts и optional поле CombatReports в AuthoritativeSnapshot. Не переименовывать и не сокращать CombatJournalEntry. Доклады производятся из тех же Engine фактов, а не повторным расчётом исхода.
- **A02 — идентичность и доставка.** Sequence докладов независима от sequence технического журнала. Batch содержит BaselineSequence текущего bootstrap, LatestSequence и новые Reports. Engine outbox выгружается в опубликованный snapshot; SnapshotMailbox объединяет недоставленные batches, SnapshotBuffer хранит входящие доклады до обработки UI. В каждой очереди лимит 4096; переполнение — явная ошибка сессии, без тихого DropOldest. Игровые часы не ожидают чтения UI. Панель после обработки сохраняет только последние 200. Успешный bootstrap фиксирует baseline до первого advance; реальные новые события первого snapshot с sequence > baseline обрабатываются.
- **A03 — bootstrap.** Для новой игры изначально известный доступный противник внутри дальности создаёт E01 при первой оценке. При Load текущие in-range противники добавляются к сохранённому набору выданных E01 как baseline без события. Затем новые входы оцениваются на авторитетных физических шагах; время доклада — время первого наблюдения условия Engine, без обещания вычисления дробного времени геометрического пересечения.
- **A04 — исправность и сканер.** Для E01 используются живой игрок, известный живой enemy, хотя бы один аппарат с положительной структурой и без действующего temporary disable, а также доступный по тем же правилам Scanner. Выключенный сканер не выдаёт E01/E02 и не воспроизводит пропущенные пуски после восстановления. Если текущий контент не назначает сканеру персонажа, показывается «Служба сканирования». Это не новая система обнаружения. После восстановления сканера ещё не доложенный противник, сейчас внутри радиуса, даёт E01. Сравнение на границе включительное (distance <= range); ordinals/нормализация ID следуют Engine.
- **A05 — участие в бою.** E02 в первой версии относится к известному enemy, фактически запустившему торпеду по игроку. Другие пуски и NPC-vs-NPC не включаются. E05 — только перехват враждебной торпеды ПРО игрока; E06 — попадание торпеды игрока по enemy. Докладчик E03/E04/E05/E06 — оператор соответствующего аппарата игрока, E07 — капитан игрока, E01/E02 — оператор доступного сканера либо служба. При нескольких подходящих сканерах стабильный moduleId определяет выбор.
- **A06 — корреляция.** EpisodeId состоит из projectileId и цели/контакта; одна итоговая E06/E07 после применения всего одного удара. Hit с нулевым изменением допустим как E06 «поражён», но E07 требует снижения брони/структуры. Отдельные попадания в один момент не объединяются. Не требуется ждать будущего snapshot, чтобы узнать результат уничтожения этого же контакта.
- **A07 — сохранение.** Optional блок GameStateData.combatReportsState с собственной Version=1 хранит Sequence и ReportedRangeTargetIds (стабильные ID, включая ранее уничтоженные). В текущем root Save17 это additive extension: отсутствие блока в существующем Save17 допустимо и инициализирует baseline; присутствующий блок валидируется строго до замены мира. Save16 и ниже по-прежнему отклоняются. Для pre-feature Save17 нельзя восстановить неизвестную историю прежних E01: исходными считаются только текущие in-range; это явная граница совместимости. Новые saves сохраняют полный набор отметок. Совместимость с запуском в старой сборке не гарантируется. Подмена root save version без синхронизации контракта и тестов запрещена.
- **A08 — ресурсы.** PNG 1024×576 (16:9), непрозрачные, без текста; при показе fit без обрезки основного действия. Каталог хранит ключи событий/вариантов, пути и цвета; role icons рисуются средствами UI, без обязательного нового набора PNG. Новый каталог/ресурсы копируются в output. Подготовка докладов/ресурсов выполняется на UI thread через GameSessionScreen.PrepareCombatReports перед screen.Render из SkiaWindow.OnRender; IScreen.Update в текущем API отсутствует. В самом Render/Draw загрузки и декодирования нет. Art preview и человеческая оценка остаются OPEN до реального просмотра.
- **A09 — геометрия.** При нехватке высоты выделять месту докладов хотя бы заголовок и один заголовок карточки, а доступное тело Object Info ограничивать и прокручивать. Раскрытие — логическое состояние даже в compact-виде; тело доклада доступно через прокрутку. За пределами минимальной матрицы не допускаются отрицательные rectangles/исключения. Точные размеры карточки — ответственность layout в пределах R01–R02.
- **A10 — статус.** Все тикеты draft/planned. Создание Board не запускает код, игру, генерацию изображений, commit, push или Graphify rebuild. Существующие незакоммиченные изменения сохраняются; HEAD и рабочее дерево сверяются заново перед реализацией.
