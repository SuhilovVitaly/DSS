# V4 «Носитель и крыло на плоскости»

Всё, что нужно, чтобы собрать симулятор боя V4 на любом языке и проверить, что он совпадает со справочной реализацией бой в бой. В папке только текущая редакция. История изменений, снимки баланса прошлых редакций и вариант A лежат отдельно, в `DB/Planning/V4.0-archive/`.

## Как собрать симулятор

1. **Числа и вычисления:** `Spec/Combat.md` §1.1. Это обязательно, без этого результат разойдётся с эталоном в первые ходы.
2. **Генератор:** `Spec/Generation.md` §1; проверить по контрольным числам.
3. **Загрузка и сборка боя:** `Data/README.md`, затем Generation §2. Проверка — 42 вызова генератора на сборку «Начального боя» и таблица сборки в `Reference/trace-seed-1.md`.
4. **Ход:** Combat §3–§7 и Generation §3. Проверка — `Reference/trace-seed-1.md` ход за ходом; первое расхождение видно по числу бросков после этапа.
5. **Все бои:** `Reference/battles.md` — каждая строка, включая число бросков.
6. **Серии:** Generation §4 → `Reference/series.md`.
7. **Интерфейс,** если нужен: `Spec/Display.md`.

## Текущие расширения DSS

Runtime использует последовательную инициативную стрельбу и механики EP-0020: сознание/уклонение, ловушки, термопоглощение и пыль. Исторические Spec/Reference сохраняют исходную одновременную модель; они не являются oracle новых исходов. Числа экспортируются из актуальных Data таблиц, дополнительные initiative — из runtime pilots.json. Текущие правила — [канонический контракт](../../../DB/Documentation/04-Engineering/TacticalBattle.md). Изменение механики DSS документируется там и в Board, без переписывания исторических reference под новый Engine.

## Текущий workflow DSS

Справочная Python-реализация в этом checkout отсутствует и не требуется (D-USER-14/15 EP-0015). Источник JSON игры — таблицы `Data/**/*.md`, размеченные `<!-- table:... -->`.

1. Изменить таблицы данных; при изменении runtime механики обновить канонический контракт; исторические `Spec/` сохранять с явной границей применимости.
2. Из корня DSS выполнить `pwsh -NoProfile -File tools/tactical-battle/Export-Content.ps1`.
3. Выполнить ту же команду с `-Check`; она проверяет экспорт без записи.
4. Выполнить тесты `ContentSyncTests` в Engine.Tests с абсолютным results-directory в workspace artifacts. Полные команды — в `tools/tactical-battle/README.md`.

`Reference/*.md` — независимые эталоны прежней реализации. Их нельзя пересоздавать по новому Engine, чтобы получить зелёные проверки. Изменение баланса требует отдельно согласованных независимых эталонов. Trace публикует координаты с шестью десятичными знаками; отсутствующие биты double из него не восстанавливаются.

## Машиночитаемые эталоны

`tools/tactical-battle/export_references.py` преобразует существующие Markdown в
`Reference/{battles,trace-seed-1,series}.json`. Это конвертер таблиц, без симуляции.
Запись разрешена только на Linux/glibc; `--check` сравнивает семантический JSON.
`geometry.json` содержит независимые крайние векторы CPython/glibc: norm, sin,
cos, atan2, hypot. Не содержит отсутствующие в источнике аргументы всех боёв.
Workflow `.github/workflows/tactical-battle.yml` выполняет экспорт и проверки.

У каждого JSON есть `header` и `data`. Header содержит версию формата, фактическую
среду конвертера, SHA256 исходных Markdown после нормализации CRLF в LF и список
непокрытых исходных полей. Среда конвертера не выдаётся за исходную среду симулятора.
Geometry хранит `arguments` и `expected` как 16 hex-символов восьми IEEE-754 bytes
в little-endian порядке; C# читает их через ReadInt64LittleEndian и
BitConverter.Int64BitsToDouble. Trace хранит опубликованные десятичные числа с
точностью шесть знаков, сборку и 19 ходов с orders/positions/shots/states и calls.
Battles хранит все 90 строк, включая опубликованные счётчики, потери, корпус и
структурную причину. Series сохраняет опубликованные проценты и округлённые
средние; точные целые суммы и timeout counts из этих чисел не восстанавливаются.
ReferenceFixtureTests проверяет fingerprint, формат IEEE и покрытие источника.

Формат JSON v2: колонка «в корму» battles.md называется rearHits (Combat §7.1). rearKills в сводках не опубликован и отмечен в missingCoverage. Миграция v1 → v2 проверяет неизменность всех чисел и исходных fingerprint на Linux до записи.
